# Changelog Format (Stage 05.8)

Defines the required structure of `05-dev/changelog.md`. Generated by the `generating-changelog` skill from git log + ADR amendments. Machine-parseable so the trunk-level release notes can aggregate per-feature changelogs without re-reading prose.

## Required structure

```markdown
---
id: CHANGELOG-001
jira: <TICKET-ID>
created: YYYY-MM-DD
version: 1
range: <base-sha>..<head-sha>
---

# Changelog — <Ticket title>

## Tickets
- <TICKET-ID> — <one-line summary>
  - FR: FR-NNN, FR-NNN
  - J: J-NN, J-NN

## Architecture changes
- ADR-NNN amended: <one-line delta>
- ADR-NNN added: <one-line subject>
- (None.) if no ADR touched

## Code summary
- Files added: <N>
- Files modified: <N>
- Files removed: <N>
- Lines added: <N>
- Lines removed: <N>
- New modules:
  - `src/path/to/new-module/` — <one-line purpose>

## Test changes
- Unit tests added: <N>
- E2E tests added: <N>
- Contract tests added: <N>
- New test files:
  - `tests/path/to/file.test.ts` — covers FR-NNN
  - `e2e/path/to/file.e2e.yaml` — covers J-NN
```

The `range` field in frontmatter is the git revision range that produced this changelog. The skill computes it from the merge-base with trunk and the head of the branch.

## Generation rules

The `generating-changelog` skill MUST:

1. Use `git log --no-merges <base>..<head>` for commits.
2. Use `git diff --shortstat <base>..<head>` for line counts.
3. Use `git diff --name-status <base>..<head>` for file additions/modifications/removals.
4. Pull ADR amendments from `04-architecture/adr/*.md` files whose `version` frontmatter changed in the range.
5. Pull FR/J references from the commit subjects (regex `\bFR-[0-9]{3}\b`, `\bJ-[0-9]{2}\b`) and from `05-dev/plan.md`.
6. Emit the file with the structure above, no extra sections, no prose.

## Validation rules

The validator (`check-merge-readiness.sh`) FAILS the merge gate if `changelog.md`:

1. Is missing.
2. Lacks frontmatter or any of `id`, `jira`, `created`, `version`, `range`.
3. Lacks any of the four required H2 sections (`Tickets`, `Architecture changes`, `Code summary`, `Test changes`).
4. Does not mention the current branch's `<TICKET-ID>` under `## Tickets`.

## Why

- **Fixed structure** makes per-feature changelogs aggregatable. Release notes are a `cat | grep`, not a writing task.
- **Counts before prose** keeps the file useful at a glance; reviewers see the size of the change before they read it.
- **ADR section explicit** prevents the "we changed the architecture quietly" failure mode.
- **Frontmatter `range`** makes the changelog reproducible: anyone can re-run the generator against the recorded SHAs.
